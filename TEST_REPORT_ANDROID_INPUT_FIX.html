Android 主控端输入指令修复

解决 Android 主控端连接 Windows 被控端时，远程桌面视频正常传输但控制指令无法送达的问题
报告生成: 2026-05-21  |  版本: 3.3.0  |  测试通过: 454/454

一、问题描述

场景：Android 手机作为主控端，通过直连模式连接 Windows 被控端。远程桌面视频传输正常，但主控端的触摸/鼠标/键盘操作无法在被控端生效。

预期行为

  1. Android 主控端触摸屏幕 → 被控端鼠标移动/点击
  2. Android 虚拟键盘输入 → 被控端键盘输入
  3. 双指缩放/滚动 → 被控端对应操作

实际行为

  • 远程视频正常显示（WebRTC 媒体流正常）
  • 分辨率协商正常（control 数据通道工作）
  • 所有输入指令无响应（鼠标、键盘、触摸均无效）

三、根因分析

经过对 Android 端 5 个源文件、Windows 端 4 个源文件、以及 shared 协议模块的完整代码审查，确定核心问题如下：

根本原因：通道选择策略缺陷

Android 端的 sendInputCommand() 及其它所有输入发送函数，均采用以下通道选择逻辑：

// 旧逻辑（有缺陷）
if (inputChannel 就绪) {
    使用 inputChannel 发送
} else if (controlChannel 就绪) {
    使用 controlChannel 发送
}

该逻辑存在以下问题：

  1. 优先使用不可靠通道：input 通道为 ordered: false, maxRetransmits: 0（无序、不重传），在某些 WebRTC 实现中可能无法正确完成协商
  2. inputChannelReady 标志依赖 onopen 事件：如果 onopen 未触发（因通道协商失败或时序问题），标志位保持 false，即使通道实际可用也无法使用
  3. 忽略已知可用的通道：control 通道已确认正常工作（分辨率请求/响应通过此通道传输），却被作为次要选择

数据流对比

步骤旧逻辑新逻辑
1. 检查 control 通道❌ 跳过，直接检查 input 优先检查
2. 检查 input 通道优先使用 作为后备
3. 通道状态依赖依赖 inputChannelReady 标志 直接检查 readyState === 'open'
4. 退化行为input 不可用 → 尝试 control control 不可用 → 尝试 input

典型代码变更示例（android/modules/input.js）

// 旧代码
const inputReady = s.inputChannel && s.inputChannelReady && s.inputChannel.readyState === 'open';
const dataReady = s.dataChannel && s.dataChannel.readyState === 'open';
if (inputReady) {
    s.inputChannel.send(message);
} else if (dataReady) {
    s.dataChannel.send(message);
}

// 新代码
const dataReady = s.dataChannel && s.dataChannel.readyState === 'open';
const inputReady = s.inputChannel && s.inputChannel.readyState === 'open';
if (dataReady) {
    s.dataChannel.send(message);      // 优先 control 通道
} else if (inputReady) {
    s.inputChannel.send(message);      // input 通道作为后备
} else {
    log('输入通道均未就绪!');          // 详细的诊断日志
}
