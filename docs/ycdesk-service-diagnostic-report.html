一、问题概述

用户反馈："服务安装成功，启动服务无反应。"

具体表现为：通过主程序安装 ycdeskservice 后，SCM（服务控制管理器）中能看到该服务，但执行 net start 或在服务管理器中点击"启动"时无任何响应，服务长期停留在 STOPPED 状态。

核心问题已解决：服务 ycdeskservice 当前状态为 Running，启动类型 Automatic，可正常由 SCM 拉起。

二、根因分析

经过对 elevate-cli.js、node-windows 源码、SCM 注册表项以及服务启动日志的综合排查，定位到以下三个相互叠加的根因：

根因 1：服务二进制直接指向 wrapper.js，缺乏 ServiceMain 入口

历史安装流程将 sc create 的 binPath 直接指向 node.exe ... wrapper.js。但 wrapper.js 本身不是 Windows Service 应用程序，没有实现 ServiceMain 回调，SCM 调用 StartServiceCtrlDispatcher 后无法在规定时间内收到 SERVICE_RUNNING 状态回报，最终触发 Error 1053：服务没有及时响应启动或控制请求。

从服务管理器的视角看：服务"无反应"。

根因 2：服务名在 node-windows 与 elevation-manager.js 之间不一致

node-windows 在调用 Service.install() 时，会把服务 id 强制转成 <id>.exe（因为 winsw 可执行文件必须与 id 同名）。

本项目配置：

  • node-windows 注册的服务名：ycdeskservice.exe（winsw 副本）
  • elevation-manager.js 中 _serviceName：ycdeskservice

两个名称不一致，导致：

  • 主程序启动时找不到 ycdeskservice，提示"服务未安装"。
  • net stop ycdeskservice 报 系统错误 2 / 名称无效。

根因 3：P/Invoke 安装残留指向 %TEMP% 临时目录

早期版本曾用 C# P/Invoke 注册服务，注册项 ImagePath 指向 Electron 解压后的临时目录（如 C:\Users\DHL\AppData\Local\Temp\3FFgFZKqEAnNu1LY9xTuJVbzpm0\resources\service-app\service-daemon.js）。

Electron 每次启动会生成新的临时目录，旧的 ImagePath 在新版本中立即失效，导致：

  • SCM 中残留一条 binPath 错误的服务。
  • 新装的 ycdeskservice 注册时报 1073 / 1057 错误。

三、解决方案

采用"先产出 winsw 文件，再纠正服务名注册"的两段式安装策略，既保留 node-windows 产物的 ServiceMain 正确性，又保证 SCM 中的服务名与 elevation-manager.js 一致。

安装流程（修改后）

Step 1
清理旧服务（防 P/Invoke 残留干扰）
sc stop "ycdeskservice" + sc delete "ycdeskservice"， 显式捕获退出码 1060（服务不存在），避免误报。
Step 2
清理 node-windows 临时服务与 daemon 目录
删除 ycdeskservice.exe（winsw 临时注册名）和 windows/service/daemon/ 目录， 保证 Service.install() 走"全新生成"分支。
Step 3
调用 node-windows Service.install()
仅用于产出 ycdeskservice.exe（winsw 副本）+ .xml + .config， 监听 'install'、'alreadyinstalled'、'invalidinstallation'、'error' 事件。
Step 4
sc create 注册 SVC_ID 对应服务
在 daemon 文件就绪后，删除 node-windows 临时注册的 ycdeskservice.exe 服务， 重新用 sc create "ycdeskservice" binPath= "ycdeskservice.exe" 注册， 启动类型 auto，显示名 YCDesk Remote Desktop Service。
Step 5
设置服务描述与失败恢复策略
sc description 写入中文描述；sc failure 设置为 restart/5000/restart/10000/restart/30000（连续三次递增间隔）。
Step 6
SCM 验证
sc qc "ycdeskservice" 读取注册信息并写入日志，确认 ImagePath、 START_TYPE、DISPLAY_NAME 与预期一致。

四、关键代码变更

主要修改集中在 elevate-cli.js（安装逻辑）。变更点概要：

1. 新增 doScInstall(settle) 内部函数

职责：

  • 校验 daemon/ycdeskservice.exe 是否存在；
  • 删除 node-windows 临时注册的服务 ycdeskservice.exe（错误码 1060 视为正常）；
  • 调用 sc create 注册 ycdeskservice，binPath 指向 winsw.exe；
  • 设置 description、failure 策略；
  • 用 sc qc 验证并打印。

2. install() 重构

// 安装策略：
//   1. node-windows 的 Service.install() 在 daemon/ 下生成 winsw.exe + .xml，
//      并用 winsw 注册服务（但 winsw 强制 service id = "<id>.exe"，与 SVC_ID 不一致）
//   2. 因此我们在 Service.install() 完成后，删除 winsw 注册的临时服务，
//      直接用 sc create + 修正后的 binPath 注册 SVC_ID 对应的服务
//   3. 这样既复用 winsw 的 ServiceMain（避免 1053 超时），又保持 SVC_ID 与
//      elevation-manager.js 一致

3. 错误码精确处理

try {
  execSync(`sc delete "${SVC_ID}"`, { stdio: 'pipe', timeout: 10000 })
} catch (e) {
  if (e && e.status === 1060) {
    log('INFO', '旧服务不存在，无需删除')
  } else {
    log('WARN', '清理旧服务时出错（继续安装）: ' + safeError(e))
  }
}

该写法使 sc delete 在服务不存在时不再被当作致命错误，安装流程可以无中断地完成。

4. daemon 目录自动清理

const daemonDir = path.join(SERVICE_APP_DIR, 'daemon')
if (fs.existsSync(daemonDir)) {
  const tempSvcName = 'ycdeskservice.exe'
  try { execSync(`sc stop "${tempSvcName}"`, { stdio: 'pipe', timeout: 5000 }) } catch (e) {}
  try { execSync(`sc delete "${tempSvcName}"`, { stdio: 'pipe', timeout: 5000 }) } catch (e) {}
  fs.rmSync(daemonDir, { recursive: true, force: true })
}

避免 node-windows 的 'alreadyinstalled' 事件在陈旧 daemon 目录上误触发。

六、发现的新问题

虽然服务本身已可正常启动运行，但日志中出现了一条新错误：

[ERROR] 未找到设备 ID，无法注册到信令服务器

6.1 根因

服务通过 loadDeviceId() 读取 C:\Users\DHL\.ycdesk\device-id 平面文件以获取设备 ID。该文件当前不存在。

6.2 现场文件清单（C:\Users\DHL\.ycdesk\）

文件状态用途
auto-connect.json存在{enabled:true, mode:signaling, serverUrl:"www.hnasvr.asia:31300"}
devices.json存在数组，deviceId="DHLDESK", alias="dhl"
device-id缺失服务期望的平面文件
service-daemon.log存在服务运行日志

6.3 问题定位

在 service-daemon.js 中：

const DEVICE_ID_FILE = path.join(CONFIG_DIR, 'device-id')

function loadDeviceId() {
  if (fs.existsSync(DEVICE_ID_FILE)) {
    return fs.readFileSync(DEVICE_ID_FILE, 'utf8').trim()
  }
  return null
}

由于 device-id 文件不存在，loadDeviceId() 返回 null，服务直接进入"待机模式"，无法连接信令服务器。

说明：devices.json 中确实存在设备 DHLDESK，但服务在 service-daemon.js 中只读取 device-id 这个平面文件，并未回退到 devices.json 的逻辑。这是 Electron 主程序（renderer 端）写入的同步契约被破坏导致。

七、后续建议

7.1 设备 ID 缺失（短期修复）

  1. 手动回填：在 Electron 主窗口的"设备管理"页面保存一次设备信息，主程序应同步生成 device-id 平面文件。
  2. 临时方案：直接将现有设备 ID 写入平面文件： 
    echo DHLDESK > C:\Users\DHL\.ycdesk\device-id

7.2 服务侧健壮性（中期改进）

修改 loadDeviceId() 增加 devices.json 回退逻辑：

function loadDeviceId() {
  // 1. 优先读取 device-id 平面文件
  const flat = path.join(CONFIG_DIR, 'device-id')
  if (fs.existsSync(flat)) {
    return fs.readFileSync(flat, 'utf8').trim()
  }
  // 2. 回退到 devices.json 的第一条记录
  const listFile = path.join(CONFIG_DIR, 'devices.json')
  if (fs.existsSync(listFile)) {
    try {
      const list = JSON.parse(fs.readFileSync(listFile, 'utf8'))
      if (Array.isArray(list) && list.length > 0 && list[0].deviceId) {
        return list[0].deviceId
      }
    } catch (e) {}
  }
  return null
}

7.3 主程序契约（长期）

建议在 devices.json 写入时同步生成 device-id 平面文件（或废弃平面文件、改用单一数据源 devices.json）。
